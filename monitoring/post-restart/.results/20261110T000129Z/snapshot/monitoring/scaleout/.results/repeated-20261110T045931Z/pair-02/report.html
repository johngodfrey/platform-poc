Order-tier scaling under a burst

Java adds an order-service pod. Wasm starts an additional runtime host pod, its providers and serving components, then verifies an order directly against that pod before adding it to HTTP routing. This scales different scopes of the application. Images may already be cached: this is a new process/pod test, not a cold image-download test. Capacity is Java Ready pods with a successful direct order / verified routable Wasm hosts.

Recovery requires two consecutive complete 15-second request-start cohorts with p95 < 500 ms, zero failures and enough completions to match the burst rate. None means no recovery observed, or the application was already healthy; consult the flags and windows in report.json. An observed capacity count is not proof of increased end-to-end throughput.
